AgentFactory — Three Eras

Each era is a set of outcomes you have to land, paired with the approach for getting there. The point isn't which files exist — it's what becomes true about the system once that era is finished.

Era I · The Framework

AgentFactory

The typed, layered Python framework built on PydanticAI, with native OpenTelemetry tracing. What an agent is, and how to run one.

Focus. Make misconfiguration impossible at construction time and make execution mechanical. Everything downstream — the API, the UI, exported projects — leans on the guarantees this era establishes.

Outcomes & how to achieve them

Outcome

"Is this an agent?" is a meaningful, framework-wide yes/no.

How

Anchor every type to a single immutable identity model with identity fields only (id, name, version, description, tags). No behavior on identity — behavior belongs to layer models that compose with it. Make every layer and the final Agent frozen=True, extra="forbid" so the answer doesn't change after the fact.

Outcome

No magic strings anywhere in user code.

How

Stand up authoritative catalogs (models, tools, errors, sinks, IO types) behind a registry. Every field that names a thing — a model id, a tool grant, an error class — gets validated against its catalog at construction. If it isn't catalogued, it doesn't exist.

Outcome

Misconfiguration fails fast and loudly — never at the first runtime call.

How

Compose the agent contract from six independent layer models, one dimension each: model → IO → tools → policy → errors → telemetry. Each layer is its own Pydantic model that validates its fields and cross-checks against the catalogs; Agent is a frozen Pydantic model whose fields are those layers, with a single model_validator for cross-layer rules. Composition (not inheritance) keeps validators isolated and centralises cross-cutting checks in one place.

Outcome

The common case is a five-line snippet, not a six-deep constructor.

How

Provide a fluent builder that lets users supply any subset of layers in any order and resolves cross-layer collisions internally. The builder owns ergonomics; the contract owns correctness. Keep them separate so adding sugar never weakens guarantees.

Outcome

An Agent isn't just a description — it can be run.

How

Add a runtime that compiles the contract into a pydantic_ai.Agent and walks the call: validate the input envelope → apply policy ceilings (timeout, token limits, usage limits) → delegate to PydanticAI for the model invocation and tool dispatch → handle errors per the agent's error policy → emit OpenTelemetry spans tagged with OpenInference attribute names → validate the output. PydanticAI owns provider clients and tool plumbing; the framework owns the typed contract, the policy envelope, and the telemetry shape. No exporter is bundled — host apps wire OTLP (Langfuse, Phoenix, Arize, Logfire, …) themselves.

Done when

  • A user installs the package, writes a builder snippet, points it at PydanticAI's TestModel, and runs an agent end-to-end with every policy, retry, and IO rule enforced.
  • Every per-layer test passes; warnings are errors; the framework depends only on pydantic, pydantic-ai, opentelemetry-api, and opentelemetry-sdk — no FastAPI, no HTTP, no bundled exporter.
  • Construction-time errors point at the bad field, not at a stack trace inside a model call three minutes later.
  • A test that installs an in-memory OTel exporter sees spans named agent.run, agent.model.invoke, and agent.tool.<id> carrying OpenInference attributes (openinference.span.kind, llm.model_name, llm.token_count.*, tool.name, …) — so Langfuse, Phoenix, and Arize render them natively without translation.
Era II · The Service

AgentComposer API

A stateless authoring backend that turns the framework into something a UI (or a script, or a CI job) can drive.

Focus. Expose the framework's questions over HTTP — "what catalogs exist?", "is this graph valid?", "what defaults make sense here?", "what would this graph look like on disk?" — without ever owning UI state. Anyone who can speak HTTP can author agents.

Outcomes & how to achieve them

Outcome

Clients learn the framework's shape at runtime — never hand-maintain a mirror of it.

How

Derive JSON schemas directly from the Pydantic layer classes and serve them. Serve every catalog as JSON too. The backend's truth is whatever the framework imports right now, so a framework upgrade automatically updates what every client sees.

Outcome

A "project" is a graph of agents, not a folder of disconnected files.

How

Promote the graph (nodes = agents, edges = "A calls B") to a first-class request payload. Validate it structurally before doing anything else: endpoints exist, recursion is within declared limits, grants are coherent. Every request carries its own graph — the server holds no session state.

Outcome

Authors describe what they want; defaults appear automatically.

How

Build a Resolver that reads each node's one-line description and fills unset fields — model tier, starter IO schema, recursion depth — then propagates implied wiring across edges (subagent grants, caller allowlists, IO compatibility). Only unset fields get touched; anything the author chose explicitly is preserved.

Outcome

Mistakes show up before they hit disk.

How

Offer preview (build one agent, return its describe-output) and dry-run (instantiate every agent in the graph in-memory) endpoints. Use the real framework to validate — don't reimplement validation rules in the API layer.

Outcome

"Export" produces a folder that works in any project that depends on the framework — with zero runtime dependency on the API.

How

Write a frozen JSON config per agent, a tiny Python loader next to each, and a package __init__.py that re-exports them. Add a graph snapshot for round-tripping. Refuse pathological destinations (filesystem root, drive root) so a typo can't nuke a machine.

Done when

  • A developer can drive the entire authoring flow from curl and end up with an importable folder.
  • Every endpoint has a test; the API has no opinions about UI; the exported tree imports cleanly with only the framework installed.
  • Restarting the server changes nothing for clients — there was no state to lose.
Era III · The Canvas

Agent Studio UI

A ComfyUI-style web editor where the layered contract becomes something you can see, drag, and connect.

Focus. Make the framework usable without writing Python. The UI is a thin shell over the API — it never reimplements validation, never hardcodes a catalog value, and never claims something is correct that the backend hasn't confirmed.

Outcomes & how to achieve them

Outcome

The UI always reflects the framework's current shape — even after a framework upgrade.

How

On boot, fetch /node-types and /catalogs and render everything from them. No hardcoded model ids, tool names, or layer fields anywhere in the frontend — every dropdown is bound to a live registry.

Outcome

Authoring feels spatial: an agent is a node, "A calls B" is an edge you draw.

How

Use React Flow for the canvas and a draggable palette for node types. Each agent node renders its six layers as collapsible sections with catalog-bound pickers. Top and bottom sockets create the calls edges that drive the Resolver's propagation rules.

Outcome

Defaults appear by themselves, but never overwrite a deliberate choice.

How

Debounce structural changes (~300 ms) and POST the graph to /presets/resolve. Parameter edits do not trigger resolve — only adds, deletes, and edges do. Provide a manual Resolve button and an auto-resolve toggle so the user is always in charge.

Outcome

Validation is the backend's job. The UI just shows the answer.

How

Keep local state optimistic for responsiveness, but every "is this OK?" answer comes from /graph/validate, /agents/preview, or /export/dry-run. Surface errors on the specific node or field they came from — never as a generic toast.

Outcome

Export is one click, and the result imports cleanly into any downstream project.

How

An export dialog takes an absolute path, calls /export, and reports success or the backend's refusal reason. The UI never writes files itself; the API owns the filesystem.

Done when

  • A user opens the app, drags two nodes, writes a description in each, draws an edge, watches defaults fill in, clicks Dry-run (green), clicks Export — and gets a folder they can import.
  • The status bar honestly reports backend state; export is disabled when disconnected.
  • Pointing the UI at a future framework version with new fields just works, because nothing about the framework was baked into the frontend.
Three eras · one chain · framework → service → canvas, never the reverse
